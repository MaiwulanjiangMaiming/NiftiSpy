致命缺陷
远程文件加载的根本性问题
BUG #1
远程预览必须全量下载文件
handlePreviewRemote → loadFileData → vscode.workspace.fs.readFile(uri)
用户打开远程文件
→
完整下载整个 .nii
→
完整解压 .gz
→
提取中间切片
→
显示预览
对于 500MB 的远程 NIfTI，用户需要等待整个文件下载完毕才能看到任何图像。VS Code 的 vscode.workspace.fs.readFile 不支持 Range 分段读取，这是架构层面的根本限制。
// LocalFileProxy.ts L523 — 致命路径
const fullData = await vscode.workspace.fs.readFile(entry.uri); // 全量读取！
const decompressed = await gunzipAsync(fullData, signal);       // 全量解压！
BUG #2
streaming gzip 实为全量加载
streamingGunzipPreview 名字叫 "streaming"，但实际上把所有解压数据块都收集到内存：
const chunks: Buffer[] = [];  // 所有块被累积
// ...
const rawData = new Uint8Array(buf.buffer, ...); // 返回完整数据
resolve({ header, axialSlice, rawData }); // rawData = 整个解压文件
它只是"早退出"（找到中间切片后停止解压），但已解压的字节全部保留。对于 1GB 解压后的 fMRI，这意味着 1GB 常驻内存。
BUG #3
Worker 内存双份持有
当 needsConversion=true（即 scl_slope≠1 或 scl_inter≠0）时，worker 同时持有两份完整体数据：
// worker.ts — 对于 1GB 的数据集，内存占用 = 2GB
const nativeData = new Float32Array(rawData.buffer, byteOff, n); // 1GB
const voxelData  = new Float32Array(n);                          // 再 +1GB！
for (let i=0; i < n; i++) voxelData[i] = nativeData[i] * slope + inter;
加上 rawData 本身（如果是 gzip 则还有压缩数据），内存峰值可达 3×体积大小。
性能缺陷
编译后本地文件也慢的原因
PERF #1
紧循环内的 throwIfAborted 调用
对于一个 256×256 的轴向切片（65536 个体素），每次切片提取都有 65536 次函数调用：
for (let i=0; i < nx*ny; i++) {
  throwIfAborted(signal); // ← 65536 次调用，每次检查 signal.aborted
  previewSlices.axial[i] = ...
}
正确做法是每 1000 次迭代检查一次，或使用 signal.addEventListener('abort', ...)。
PERF #2
gunzipSync 阻塞 Worker 线程
使用 fflate 的 gunzipSync 时，整个 Worker 被阻塞，无法响应取消信号、进度报告或其他消息。对于 300MB 的压缩 fMRI，这可能造成数秒卡顿：
rawData = gunzipSync(compressedData); // 阻塞整个 Worker 线程！
应使用 fflate 的 gunzip（异步版本）或 DecompressionStream（原生）。
PERF #3
Float32Array → JSON → Float32Array 序列化往返
预览切片在某些路径下仍使用 JSON 序列化：
slices: {
  axial: Array.from(axialSlice),   // Float32Array → Array → JSON字符串 → 网络 → 解析
  ...
}
256×256 切片 = 65536 个 float → 约 1MB ASCII JSON vs. 256KB 原生二进制。preview-bin 端点存在但某些流程绕过了它。
PERF #4
Slice 双重缓存浪费内存
每个 slice 结果同时写入 globalSliceCache 和 entry.sliceCache：
globalSliceCache.set(cacheKey, { data: buf, timestamp: now });
entry.sliceCache?.set(cacheKey, { data: buf, timestamp: now }); // 同一个 buf！
两个 Map 持有相同的 Buffer 引用，清理逻辑也因此复杂。
PERF #5
500+ 行 Worker 代码完全重复
handleLoadVolume 和 handleLoadVolumeFromData 是几乎完全相同的拷贝：解析头部、创建 TypedArray、计算 min/max、提取预览切片、传输体数据——每段逻辑重复两遍。任何 bug 修复都需要同时修两处。
PERF #6
compressResponse 双缓冲
HTTP 响应压缩时，整个响应体先在内存中 gzip，再发送：
zlib.gzip(data, (err, compressed) => {
  res.end(compressed); // 原始 + 压缩 = 2× 内存
});
应使用流式压缩：res.pipe(zlib.createGzip())。
架构问题
设计层面的局限
ARCH #1
HTTP/1.1 代理
本地代理只支持 HTTP/1.1，快速切片滚动时请求会排队。HTTP/2 的多路复用能同时处理多个切片请求。
ARCH #2
WebGL 1.0 着色器
着色器使用 #version 100（WebGL1）。VS Code webview 支持 WebGL2，提供更好的浮点纹理、更大的纹理尺寸和更快的 GLSL。
ARCH #3
无真正的 LOD 金字塔
LOD 端点只下采样单个轴向切片，没有完整的多分辨率体金字塔（类似 Google Maps 瓦片）。
ARCH #4
无 Range 请求切片服务
Slice 端点在提取前加载完整的原始数据。对于未压缩的 .nii，切片字节偏移是已知的，完全可以只发起 Range 请求。
ARCH #5
localResourceRoots 安全问题
vscode.Uri.joinPath(uri, '..') 给 webview 开放了 NIfTI 文件所在的整个父目录访问权限。
ARCH #6
单 Worker 串行处理
每个 viewer 只有一个 Worker。轴向/冠状/矢状切片提取是独立的，完全可以并行在 Worker 池中处理。

## 问题根源分析

### 最致命的：远程文件必须全量下载才能预览

整个远程路径的调用链是这样的：

```
handlePreviewRemote
  → loadFileData(entry)
    → vscode.workspace.fs.readFile(uri)   ← 下载整个文件
    → gunzipAsync(fullData)               ← 解压整个文件（阻塞）
  → extractPreviewSlices(rawData, header) ← 此时才提取中间切片
```

VS Code 的 `workspace.fs` 是为代码文件设计的，不支持 HTTP Range 请求，所以对于 SSH 远程的 500MB NIfTI，必须全量传输才能看到第一张切片。这是架构层面的根本限制，不是参数调优能解决的。

### 本地编译后变慢：Worker 的 gunzipSync 阻塞问题

本地 `.nii.gz` 文件在 Worker 里用的是 fflate 的 `gunzipSync`，这是同步操作，会冻结整个 Worker 线程数秒钟。在开发环境下用 `ts-node` 运行时感受不明显，但编译后打包成 VSIX、通过 Extension Host 的 IPC 通道与 Worker 交互时，这个阻塞会让 VS Code 的整个响应感变差。

### Worker 500行代码重复

`handleLoadVolume` 和 `handleLoadVolumeFromData` 几乎完全相同，任何性能优化都需要改两处，这也是目前 bug 难以追踪的原因之一。

## 重构的核心策略

**第一优先：解决本地 .nii 的切片服务**，把 `/slice` 端点改成只读取那几个字节：

```typescript
// 改造后的 handleSlice — 只读取目标切片字节
async handleSlice(entry, axis, idx, res, req) {
  const header = await this.getHeader(entry);
  const { nx, ny, nz, voxOffset, bytesPerVoxel } = header;
  
  const [start, end] = computeSliceByteRange(axis, idx, header);
  // 对本地文件: 只读这几百KB，不加载整个文件
  const sliceBytes = await readLocalFilePartial(entry.uri.fsPath, start, end);
  const slice = extractAxialSliceFromRange(sliceBytes, header);
  res.end(Buffer.from(slice.buffer));
}
```

**第二优先：Worker 改异步解压**：

```typescript
// 替换 gunzipSync → 异步版本，Worker 不再卡死
import { gunzip } from 'fflate';

const rawData = await new Promise<Uint8Array>((res, rej) =>
  gunzip(compressed, (err, data) => err ? rej(err) : res(data))
);
```

**第三优先：远程文件绕过 VS Code FS**，对于 HTTP/HTTPS 远程 URI，直接在 Extension Host 用 Node.js 原生 `http.get` 发 Range 请求，完全绕过 `vscode.workspace.fs`：

```typescript
// Extension Host 直接发 HTTP Range 请求（绕过 VS Code FS 抽象层）
async fetchRemoteHeaderBytes(url: string): Promise<Uint8Array> {
  return new Promise((resolve, reject) => {
    const req = https.get(url, { headers: { Range: 'bytes=0-543' } }, res => {
      const chunks: Buffer[] = [];
      res.on('data', c => chunks.push(c));
      res.on('end', () => resolve(new Uint8Array(Buffer.concat(chunks))));
    });
    req.on('error', reject);
  });
}
```

对于 SSH 远程（`vscode-remote://` scheme），目前没有官方 API 支持 Range 读取，但可以通过 VS Code 的 `TaskProvider` 在远端执行一个小 Python 脚本输出指定字节范围，是迂回但有效的方案。

**长期方向**：参考 neuroglancer 和 ITK-SNAP 的分块设计，把体数据组织成 Zarr/N5 格式的分块金字塔，配合 HTTP/2 多路复用代理和 WebGL2 GPU 渲染，是真正能媲美 niivue 速度同时解决远程大文件问题的架构。




然后非常重要的是，当前我们的代码库比较乱，需要遵循 SOLID 和 SPY 原则，进行大面积的重构，但是不是在损坏功能的基础上，这个不能变，要维持当前的功能不能损坏
