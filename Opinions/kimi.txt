## 一、问题根因深度诊断

你的 NiftiSpy 当前架构存在**五个致命瓶颈**，这些问题在本地编译构建后被放大，在远程 SSH 场景下呈指数级恶化：

### 1.1 VS Code Webview 的数据管道瓶颈（最严重）
VS Code 扩展的 Webview 与 Extension Host 之间通过 **JSON 消息序列化** 传递所有数据。当你传输一个 512×512×512 的 Float32 体积（约 536MB），即使只是更新一个切片，数据也需要经过：
> 文件系统 → Extension Host (Node.js) → JSON 序列化 → Webview (Chromium) → JavaScript 堆 → Canvas

**远程场景下路径更长**：
> 远程文件系统 → SSH 流 → VS Code 远程代理 → Extension Host → JSON 序列化 → Webview → JS 堆

**JSON 序列化大 ArrayBuffer 是性能杀手**，且 Webview 的 `postMessage` 有消息大小限制和异步延迟。

### 1.2 渲染路径选择错误
你当前默认使用 **Canvas 2D** 渲染。Canvas 2D 对医学图像的窗宽窗位（Window/Level）调整、缩放、MPR（多平面重建）切片提取全部是 **CPU 端像素级操作**。这意味着每次调整对比度或滚动切片，都在进行数百万像素的 CPU 循环计算。

ITK-SNAP 使用原生 C++ 直接操作 GPU 纹理；Niivue 使用 WebGL2 的 3D 纹理直接在 GPU 中提取任意切片。你的 Canvas 2D 路径与两者有**数量级的性能差距**。

### 1.3 体积数据的内存模型缺陷
当前架构将**完整解压后的体积数据**保存在 Webview 的 JavaScript 堆中。这导致：
- **内存碎片**：V8 对数百 MB 的连续 TypedArray 管理效率低下
- **GC 停顿**：大体积数据触发频繁的垃圾回收，造成界面卡顿
- **重复拷贝**：从 Extension Host 到 Webview 是一次拷贝，Canvas 绘制是另一次拷贝

### 1.4 远程 I/O 的"全量加载"陷阱
对于 `.nii.gz` 文件，当前实现可能需要**完整下载并解压**后才能查看第一个切片。Niivue 也有类似问题。理想方案应实现：
- **头部优先**：先读取 352 字节的 NIfTI 头部获取维度信息
- **切片级随机访问**：无需解压整个文件就能读取任意切片
- **预测性预取**：根据滚动方向预取后续 2-3 个切片

### 1.5 计算与渲染耦合在单线程
窗宽窗位调整、方向重采样、坐标映射等计算与 UI 渲染竞争主线程资源。当体积较大时，单帧计算可能超过 16ms，导致掉帧。

### 2.2 核心技术选型决策

| 组件 | 当前方案 | 重构方案 | 理由 |
|------|---------|---------|------|
| **渲染 API** | Canvas 2D (默认) | **WebGPU** (主) + WebGL2 (回退) | WebGPU 支持计算着色器和显式内存管理，3D 纹理采样效率更高。WebGL2 通过 ANGLE 映射到各平台原生图形 API。 |
| **核心引擎** | JavaScript + 可选 Rust Native | **Rust → WASM** (核心) + 可选 Native | WASM 性能接近原生，且与 JS 零拷贝交互。Rust 提供内存安全和极致性能。 |
| **体积存储** | JS ArrayBuffer (完整) | **GPU 3D Texture** + 分块 WASM 内存 | 将体积数据驻留 GPU，切片提取在片段着色器中完成，CPU 零开销。 |
| **远程文件** | 全量下载 | **HTTP Range 请求** + **Indexed GZIP** + 本地磁盘缓存 | 实现切片级随机访问，无需下载完整文件。 |
| **通信机制** | Webview postMessage (JSON) | **SharedArrayBuffer** + **OffscreenCanvas** + 控制消息 | 大数据走共享内存，控制消息走轻量 JSON。 |

## 三、分层详细设计方案

### 3.1 I/O 层：流式文件引擎（解决远程慢的核心）

#### A. 索引化 GZIP 随机访问
标准 GZIP 不支持随机访问，必须从文件头开始解压。你需要集成 **`indexed_gzip`** 原理的 Rust 实现：

**首次打开大文件时**，后台 Worker 构建索引（耗时约 1-3 秒，与文件大小线性相关但常数极小）。**之后任意切片访问延迟 < 50ms**。

#### B. VS Code 远程文件流式读取
针对 VS Code Remote/SSH，不要通过 Extension Host 读取完整文件再传给 Webview。而是：

1. **Extension Host 端**：注册自定义 `FileSystemProvider`，暴露文件的 `read(range)` 能力
2. **Webview 端**：通过 `fetch()` 向本地代理端点发起 **HTTP Range 请求**
3. **本地代理**：将 Range 请求映射为 VS Code 的 `vscode.workspace.fs.readFile(range)` 调用

```typescript
// Webview 中的流式读取器
class VSCodeFileStream {
    async readRange(offset: number, length: number): Promise<<Uint8Array> {
        const response = await fetch(`vscode-file-proxy://${this.uri}`, {
            headers: { 'Range': `bytes=${offset}-${offset + length - 1}` }
        });
        return new Uint8Array(await response.arrayBuffer());
    }
}
```

#### C. 多级缓存策略
```
L1: GPU 3D Texture (当前活动体积)
L2: WASM 内存池 (最近 3 个方向切片缓存)
L3: IndexedDB 磁盘缓存 (远程文件分块缓存，按 256KB 块)
L4: 远程文件系统 (原始数据源)
```

### 3.2 数据层：分块体积缓存与 LOD

#### A. 内存池管理器

#### B. LOD (Level of Detail) 金字塔
对于超大体积（如 1024×1024×1024），构建多分辨率金字塔：
- **LOD0**: 原始分辨率（GPU 显存允许时）
- **LOD1**: 1/2 分辨率（快速预览）
- **LOD2**: 1/4 分辨率（缩略图/初始加载）

**初始加载策略**：
1. 0ms: 读取头部，显示空白画布 + 维度信息
2. 50ms: 加载 LOD2（约 1/64 数据量），显示低分辨率预览
3. 200ms: 加载当前可见切片的 LOD1
4. 1000ms: 异步加载 LOD0 完整数据到 GPU

### 3.3 计算层：WASM 计算着色器预处理器

将**所有像素级计算**从 CPU 迁移：

| 操作 | 当前实现 | 重构实现 |
|------|---------|---------|
| **窗宽窗位** | JS 循环遍历像素 | GPU 片段着色器 uniform 调整 |
| **MPR 切片提取** | CPU 重采样 | GPU 3D 纹理 `textureSample` |
| **方向重采样** | JS 矩阵乘法 | WASM SIMD + GPU 顶点变换 |
| **直方图/统计** | JS 单次遍历 | WebGPU 计算着色器并行归约 |

#### WebGPU 计算着色器示例（窗宽窗位 + 切片提取）
```wgsl
@group(0) @binding(0) var volume_tex: texture_3d<f32>;
@group(0) @binding(1) var tex_sampler: sampler;
@group(0) @binding(2) var<<uniform> params: WindowLevelParams;

struct WindowLevelParams {
    window_center: f32,
    window_width: f32,
    slice_index: f32,
    axis: u32, // 0=axial, 1=coronal, 2=sagittal
};

@fragment
fn main(@builtin(position) fragCoord: vec4<f32>) -> @location(0) vec4<f32> {
    let tex_coord = compute_slice_uv(fragCoord.xy, params.axis, params.slice_index);
    let voxel = textureSample(volume_tex, tex_sampler, tex_coord).r;
    
    // 窗宽窗位映射在 GPU 完成
    let min_val = params.window_center - params.window_width / 2.0;
    let max_val = params.window_center + params.window_width / 2.0;
    let normalized = clamp((voxel - min_val) / params.window_width, 0.0, 1.0);
    
    return vec4<f32>(normalized, normalized, normalized, 1.0);
}
```

### 3.4 渲染层：WebGPU 3D 纹理管线

#### A. 为什么 3D 纹理是革命性的
Niivue 使用 WebGL2 的 3D 纹理实现了任意方向切片提取。 你的重构应升级到 WebGPU，因为：

1. **显式内存管理**：WebGPU 的 `GPUTexture` 有明确生命周期，无隐式状态机开销
2. **计算着色器**：可在同一管线中做预处理（去噪、增强）和渲染
3. **命令缓冲区**：批量提交渲染命令，减少 CPU 开销
4. **现代纹理格式**：原生支持 `r16float`、`r32float` 等医学图像常用格式

#### B. 渲染架构
```
┌─────────────────┐
│   3D Volume     │  ← GPUTexture (r16float/r32float)
│   Texture       │
└────────┬────────┘
         │ textureSample
         ▼
┌─────────────────┐
│  MPR/Slice      │  ← 顶点着色器生成切片平面
│  Vertex Shader  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Fragment       │  ← 片段着色器提取体素 + 窗宽窗位 + 调色板
│  Shader         │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Canvas/Display │
└─────────────────┘
```

**关键优势**：当用户滚动切片时，**不需要重新上传任何纹理数据**，只需更新 `slice_index` uniform。这是**零带宽**操作，可实现 144Hz 流畅滚动。

#### C. 多视图同步渲染
对于 Axial/Coronal/Sagittal 三视图 + 3D MIP：
- 使用 **单个 3D Texture** 共享给所有视图
- 每个视图独立 uniform buffer，**单 Pass 渲染**或**并行计算着色器**生成
- WebGPU 的 `renderBundle` 预录制静态管线状态，减少每帧开销

### 3.5 交互层：预测性预取与异步 UI

#### A. 滚动预测引擎
```typescript
class PredictivePrefetcher {
    private scrollVelocity: number = 0;
    private lastScrollTime: number = 0;
    
    onScroll(sliceIndex: number) {
        const now = performance.now();
        const dt = now - this.lastScrollTime;
        const velocity = (sliceIndex - this.lastSlice) / dt;
        
        // 根据速度预测未来 3 个切片
        const prefetchSlices = [];
        for (let i = 1; i <= 3; i++) {
            prefetchSlices.push(sliceIndex + Math.sign(velocity) * i);
        }
        
        // 异步预取到 L2 缓存
        this.volumeCache.prefetchSlices(prefetchSlices);
    }
}
```

#### B. 防抖与节流策略
- **滚动事件**：使用 `requestAnimationFrame` 节流，16ms 内合并多次更新
- **窗宽窗位拖拽**：在 GPU uniform 中实时更新，**不触发任何 CPU 计算**
- **缩放/平移**：变换矩阵在顶点着色器中应用，零 CPU 开销

## 四、VS Code 扩展特定优化

### 4.1 从 Webview Panel 迁移到 Custom Editor API
VS Code 的 `CustomEditorProvider` 允许你：
- 直接访问文件的 `Uint8Array` 数据，无需通过 Webview 传输
- 使用 `extension.fs` 的流式读取能力
- 更好的生命周期管理（激活/暂停/恢复）

### 4.2 SharedArrayBuffer 零拷贝通信
如果必须使用 Webview，使用 `SharedArrayBuffer` 替代 `postMessage`：

```typescript
// Extension Host
const sharedBuffer = new SharedArrayBuffer(512 * 512 * 4); // 预分配
const worker = new Worker('decoder.js');
worker.postMessage({ type: 'init', buffer: sharedBuffer }, [sharedBuffer]);

// Worker 直接写入共享内存，Webview 直接读取
```

**注意**：需要设置 COOP/COEP 头，VS Code Webview 支持通过 `enableProposedApi` 或特定配置实现。

### 4.3 远程场景的特殊优化
- **本地磁盘代理缓存**：在本地 `%APPDATA%/NiftiSpy/cache/` 缓存远程文件分块
- **差异同步**：只传输变化的分块（如果文件在远程被修改）
- **连接质量自适应**：检测带宽，动态调整 LOD 级别
